## Commands

- `npm run lint` — oxlint (`src/`, `test/`). There is no ESLint config; do not add one.
- `npm run test` — unit tests via Vitest (`*.spec.ts`, globals enabled, no imports needed).
- `npm run test:e2e` — e2e via Vitest with a separate config (`vitest.config.e2e.ts`, matches `*.e2e-spec.ts`). A unit run will NOT pick up e2e specs — always run both.
- `npm run build` — `nest build`; this is the typecheck step (no `tsc --noEmit` script exists).
- `npm run format` — Prettier (single quotes, trailing commas).
- Verify order: `lint` -> `test` -> `test:e2e` -> `build`.
- Dev server: `npm run start:dev` (port from `PORT` env, default 3000). Swagger UI at `/api`.

## Gotchas

- ESM: package.json has `"type": "module"` and tsconfig uses `module/moduleResolution: nodenext`. All relative imports must use explicit `.js` extensions even in `.ts` files: `import { AppModule } from './app.module.js'`. Omitting `.js` breaks build and tests.
- Vitest replaces Jest: don't create jest configs or `jest.*` scripts. Test files live next to source (`*.spec.ts`) except e2e, which lives in `test/`.
- `app.module.ts` contains `@nestjs/observe` with placeholder `appKey`/`appSecret` values — don't treat them as real credentials.
- tsconfig has `strict: true` but `strictPropertyInitialization: false`; `types` includes `vitest/globals`.
- Control de Almacén (`src/features/almacen/`): toda mutación de stock pasa por `shared/inventario-ledger.ts` dentro de una transacción y con SQL crudo (`db.raw.sql`, cantidades/costos `numeric` casteados a text). `tx` no expone `raw`: arme el plan con `db.raw.sql` y ejecútelo con `tx.query(plan).toArray()` (filas) o `tx.execute(plan)` (filas afectadas). `test/almacen.e2e-spec.ts` escribe en la BD de `DATABASE_URL` y limpia sus propios datos. Plan y decisiones: `planes/04-control-almacen.md`.
- Compras (`src/features/requerimientos/` + `src/features/almacen/recepciones/`): FUR -> aprobación -> OC (`documentosOrigen`) -> recepción -> ingreso `COMPRA`. Los saldos (aprobado -> ordenado -> recibido) **no se guardan**: se calculan en SQL (`requerimientos/shared/requerimiento-saldos.ts`, `almacen/shared/oc-saldos.ts`). Todo lo que consume saldo corre en `db.transaction` con `FOR UPDATE` del FUR o de la OC; dentro de la transacción use `tx.orm.public` y arme la respuesta **después del commit** (otra conexión no ve filas sin confirmar). Un FUR solo genera OC en `APROBADO`; la OC con ingresos (aunque estén anulados) no admite reemplazar su detalle ni eliminarse. Soles = símbolo `S/…`, vacío o `moneda_id` `PEN` (los datos históricos mezclan ids); si no, la recepción exige `tipo_cambio`. Los enums de Prisma Next se guardan como `text` con `CHECK`. Para listas de ids use `= ANY(string_to_array(${csv}::text, ',')::int[])`. `test/compras-flujo.e2e-spec.ts` escribe en la BD de `DATABASE_URL` y limpia sus datos. Plan y decisiones: `planes/05-requerimientos-fur.md`.
- Módulo administrativo (plan 06): `requerimientos/cotizaciones/` + `tesoreria/` + `documentos/administracion/`. Una compra se cotiza (de 1 a n proveedores, FUR `ENVIADO`), se cierra el cuadro (`COTIZADO`) y **quien aprueba elige un ganador** (el sistema no sugiere ni exige el más barato); al aprobar se generan en la misma transacción las OC/OS del ganador (`requerimientos/shared/generar-documentos-origen.ts` + `documentos/shared/documento-origen-insert.ts`). Planillas, caja chica, gastos financieros y servicios se aprueban desde `ENVIADO` y generan un documento por beneficiario. `documentosOrigen.total` es **bruto** (monto + IGV); el neto a pagar, el vencimiento (OC: última recepción + días de crédito) y el estado de pago **se calculan** en un SQL único (`tesoreria/shared/documentos-consulta.ts`); las reglas de IGV, detracción 10 % y retención 3 % están en `tesoreria/shared/tributos.ts` (cambie las tasas solo allí). Los pagos se programan **solo los viernes** (o `urgente` con motivo), pueden ser parciales y el comprobante es `CP-`. Anular un DO libera el saldo del FUR (las consultas de saldo excluyen `ANULADO`). El tipo de cambio diario (`tipo_cambio_diario`, se usa el de venta) lo usan pagos, detracciones, recepción de almacén y tablero. `test/modulo-administrativo.e2e-spec.ts` y `test/compras-flujo.e2e-spec.ts` escriben en la BD de `DATABASE_URL` y limpian sus datos. Plan y decisiones: `planes/06-modulo-administrativo-cotizaciones-pagos.md`.
- Permisos por persona (plan 08, `planes/08-areas-y-cargos.md`): el **rol** da las acciones por módulo (`rol_permiso`), el **área** del usuario (`usuarios.id_area`) habilita módulos (`area_modulo`: no / solo ver / completo; un área sin módulos no restringe; Administración y `modulos` no dependen del área) y las **excepciones** (`usuario_permiso`, solo las gestiona el Administrador) reemplazan un módulo para una persona. Todo se combina en `platform/auth/permisos.ts → detallePermisosModulo`; el guard (`PermisosRolService.obtenerParaUsuario`) y `GET /auth/mis-permisos` usan la misma función. Alcance global = Administrador o usuario sin área. `test/areas-permisos.e2e-spec.ts` crea y borra sus propios datos.
- Dashboard de Operaciones (`src/features/operaciones-obra/`): el detalle de una obra usa el módulo de permisos `obra` y las vistas con todas las obras (`portafolio/`, `avisos/`) el módulo `operaciones` (sin permisos por defecto; solo el Administrador). El cálculo es **puro** y vive en `shared/control-avance/` (`motor.ts` → `calcularObra(entrada, hoy)`: sin Nest ni BD, `hoy` se inyecta con `hoyLima()`); `carga-obra.ts` arma la entrada desde la BD (`cargarObra`, y `cargarObras` en lote para el portafolio). Semanas de lunes a domingo, días laborables de lunes a sábado, tolerancia de 0,5 pp. El avance real, el programado y la situación **no se guardan**: se calculan al leer. Todo cambio escribe su evento (`registrar-evento.ts`) en la misma transacción; los avisos que dependen del tiempo (pasó a Retrasada, plazo vencido) se generan al leer el portafolio (`eventos-derivados.ts`, a lo sumo uno por minuto, sin planificador). Los golden tests comparan con los Excel reales (`shared/control-avance/__fixtures__/op-26-0xx.json`). `importacion/` lee el Excel por proyecto (`POST …/importar-excel`, vista previa con `confirmar=false`); `avisos/` guarda lo leído y las preferencias de la campana (`obra_aviso_usuario`, acciones personales con `@Accion('ver')`). `test/operaciones-obra`, `operaciones-portafolio` y `operaciones-importacion` escriben en la BD de `DATABASE_URL`, limpian sus datos y deben correr **en serie** (`npx vitest run --config ./vitest.config.e2e.ts --no-file-parallelism`: comparten el usuario `E2E-ADMIN`). Plan y decisiones: `docs/documentacion_aplicacion/plan_implementacion_sdd_operaciones.md` y `planes/07-dashboard-operaciones.md`.
- Cadena presupuesto Meta → obra → liquidación (GRP, `docs/documentacion_aplicacion/features-nuevas/plan-implementacion-sdd-GRP.md`): el estado del presupuesto vive en `estado_ppto` (`presupuestos/aprobacion/estados.ts`; `Estado` es solo un espejo legado) y **no se cambia por PATCH**: `POST /presupuestos/:id/{aprobar,limpiar-vacios,nueva-version}` (aprobar exige el permiso `aprobar` y captura la estructura de la obra con `capturar-estructura.ts`). El cronograma semanal es solo lectura (escritura = 410). Liquidar (`operaciones/obra/:id/liquidacion`) pasa el CC de `POR LIQUIDAR` a `CERRADO` y no se cierra a mano. La **subfase** (`ppto_DetalleFasesCate.id`) viaja por línea en FUR, OC/OS directas y salidas CONSUMO (`id_ppto_detalle_categoria`); se valida con `presupuestos/shared/subfase-presupuesto.ts` (debe ser de un presupuesto aprobado del mismo CC; en salidas es obligatoria si el CC tiene un Principal aprobado) y `GET /subfases?id_centro_costo=` la lista. La OC hereda la subfase de la línea del FUR al **leer** (no se copia). `generar-furs` exige el presupuesto aprobado y genera **una línea por (producto, subfase)**: por eso un FUR de compra puede repetir producto en subfases distintas. El gasto por subfase (`operaciones-obra/shared/gasto-subfase.ts`, `GET operaciones/obra/:id/gasto`) se calcula al leer: directo (servicios de OC/OS), indirecto (PECOSA) y compromiso (`OC de bienes − indirecto`, sin bajar de 0). `test/presupuesto-aprobacion`, `obra-liquidacion`, `subfase-gasto` y `recorrido-grp` (recorre toda la cadena por API) escriben en la BD de `DATABASE_URL` y limpian sus datos. Plan y decisiones: `planes/08-cadena-presupuesto-obra.md` y `docs/documentacion_aplicacion/features-nuevas/plan-implementacion-sdd-GRP.md`.
- Mayúsculas (GRP S-11): `platform/http/mayusculas.interceptor.ts` (global, `APP_INTERCEPTOR`) convierte a mayúsculas el cuerpo de POST/PUT/PATCH **antes** del `ValidationPipe`. No toca claves que cuadren con `PATRON_CLAVES_EXCLUIDAS` (correo, usuario, clave, url, observ…), códigos `Id…`, los campos `@IsIn/@IsEnum` con valores con minúsculas **del DTO de esa ruta** (y los anidados), los marcados con `@SinMayusculasCampo()` ni las rutas con `@SinMayusculas()` (auth, menú, permisos, roles, usuarios, características de producto). Un campo nuevo que el sistema compare con minúsculas debe usar `@IsIn`, `@SinMayusculasCampo()` o su ruta `@SinMayusculas()`. Los e2e comparan textos ya en mayúsculas.
- Periodo (GRP): año activo de `periodo_fiscal` y año de `fecha_inicio` (`proyectos-catalogos/periodo-fiscal/validar-periodo.ts`), validado en CC y presupuesto solo cuando el periodo o el inicio cambian.
- Presupuesto Comercial (GRP SP-16): no se digita, se calcula (`presupuestos/aprobacion/comercial.ts`, `GET presupuestos/:id/comercial`): cada fase del Meta con el total sin IGV de la cotización ganadora de su FUR (en soles); sin ganadora iguala al Meta.
- `prisma migration plan` toma `migrations/app/refs/db.json` como punto de partida; si está atrasado respecto a la última migración, pase `--from <hash del contrato vigente>` o generará de nuevo tablas ya creadas. Tras editar `migration.ts` a mano ejecute `node migrations/app/<dir>/migration.ts` desde la raíz del backend para regenerar `ops.json`/`migration.json`.
